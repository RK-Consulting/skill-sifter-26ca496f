# Phase 7 — Offer, Joining, and Billing Workflow

**Status:** Architecture baseline
**Runtime model:** Candidate × Requirement
**Prerequisite:** Phase 6 Selection

## 1. Lifecycle position

```text
Requirement
     ↓
Candidate × Requirement
     ↓
Screening
     ↓
Submission
     ↓
Feedback
     ↓
Interview
     ↓
Selection
     ↓
Offer
     ↓
Offer Accepted
     ↓
Joining
     ↓
JOINED
     ↓
Billing
```

## 2. Core rule

Selection is not billable.

Billing eligibility is created only when the candidate actually joins the selected requirement.

**Billing date = actual joining date.**

## 3. Offer

### Entry gate

An Offer requires a Selection record for the same Candidate × Requirement with:

```text
decision = selected
```

### Offer states

```text
draft → offered → accepted
             ├→ declined
             ├→ expired
             └→ withdrawn
```

An Offer may contain:
- offer reference
- offered date
- expected joining date
- compensation / package details
- offer terms
- notes
- acceptance/decision timestamp
- audit timestamps

Compensation offered to the candidate is not the same thing as the recruitment firm's billing amount.

### Offer rules

1. Candidate and Requirement must belong to the authenticated tenant.
2. Selection must exist for the same pair.
3. Selection decision must be `selected`.
4. Only one active Offer may exist for a Candidate × Requirement.
5. An accepted Offer is the gate for Joining.
6. Offer state must not mutate Candidate master state.

## 4. Joining

Joining represents the actual outcome of the recruitment transaction.

### Joining states

```text
scheduled
   ↓
joined

scheduled → no_show
scheduled → cancelled
```

Expected joining and actual joining are separate facts.

### Joining rules

1. Candidate and Requirement must belong to the authenticated tenant.
2. An accepted Offer must exist for the same pair.
3. A successful joining is allowed only once for a Candidate × Requirement.
4. `joined` requires `actual_joining_date`.
5. Recording `joined` establishes the Candidate × Requirement outcome as `JOINED`.
6. Candidate master status is not changed to joined.

Minimum Joining data:
- Offer reference
- expected joining date
- actual joining date
- joining status
- joining notes
- audit timestamps

## 5. Billing

Billing represents the recruitment firm's commercial claim generated by successful joining.

### Billing gate

```text
Joining.status = joined
        ↓
Billing eligible
        ↓
billing_date = actual_joining_date
```

Selection, Offer creation, and Offer acceptance must never independently create billing eligibility.

### Minimum Billing data

- Candidate
- Requirement
- Client
- Joining reference
- billing date
- billing amount
- billing basis/commercial terms
- currency
- billing status
- invoice/reference number where applicable
- due date where applicable
- audit timestamps

### Initial billing states

```text
pending → invoiced → paid
              └→ cancelled
```

These states describe SkillSifter's recruitment billing record. They do not constitute a general accounting ledger.

## 6. Candidate boundary

Candidate remains a reusable master record.

```text
Candidate A
  ├── Requirement 101 → JOINED → BILLED
  └── Requirement 205 → Interviewing
```

No Candidate columns are introduced for:
- offer status
- joining status
- billed status
- invoice status

All downstream state remains scoped to Candidate × Requirement.

## 7. API

```text
GET  /api/v1/candidates/{candidateId}/requirements/{requirementId}/offer
POST /api/v1/candidates/{candidateId}/requirements/{requirementId}/offer

GET  /api/v1/candidates/{candidateId}/requirements/{requirementId}/joining
POST /api/v1/candidates/{candidateId}/requirements/{requirementId}/joining
PUT  /api/v1/candidates/{candidateId}/requirements/{requirementId}/joining

GET  /api/v1/candidates/{candidateId}/requirements/{requirementId}/billing
POST /api/v1/candidates/{candidateId}/requirements/{requirementId}/billing
```

Mutation rules will be enforced in the domain service and database constraints, not only by the frontend.

## 8. Database approach

New migrations start after migration 031.

Historical migrations remain unchanged.

Candidate × Requirement and tenant indexes are required for all three records.

Recommended uniqueness:
- one active Offer per Candidate × Requirement
- one successful Joining per Candidate × Requirement
- one Billing record per Candidate × Requirement unless a future commercial decision explicitly permits multiple billing milestones

## Acceptance criteria

- Offer cannot exist without selected Candidate × Requirement.
- Joining cannot be confirmed without accepted Offer.
- `joined` requires actual joining date.
- Billing cannot be created before joining.
- Billing date equals actual joining date.
- Candidate master state remains unchanged.
- Cross-tenant access is rejected.
- Historical Assignment migrations remain untouched.
- CI remains green after each sub-phase.
