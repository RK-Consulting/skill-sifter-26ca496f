# v0.4.0 Architecture Foundation — Issue Backlog

**Milestone:** `v0.4.0 — Architecture Foundation`  
**Purpose:** establish approved design boundaries for later releases. This milestone must not implement later recruitment or commercial features.

## Common issue requirements

Every issue must name its owner, milestone, dependencies, affected documents, tenant/security impact, and acceptance criteria. Any decision with a durable architecture impact is recorded in an ADR before implementation.

| ID | Title | Depends on | Acceptance criteria |
| --- | --- | --- | --- |
| V04-01 | Reconcile the v0.3.0 release baseline | — | README, changelog, release notes, architecture status, and GitHub milestone identify v0.3.0 consistently; discrepancies are resolved or explicitly tracked. |
| V04-02 | Decide tenant identity and isolation approach | V04-01 | ADR states whether and how immutable tenant IDs are introduced; upgrade path, data isolation enforcement point, tests, and compatibility risks are specified. |
| V04-03 | Define the Client and Requirement domain model | V04-01 | Proposed entities, relationships, ownership, required attributes, lifecycle, and v0.5 migration approach are documented; the `jobs` to `requirements` decision is explicit. |
| V04-04 | Define Recruitment Assignment and historical snapshots | V04-03 | ADR defines the candidate–requirement transaction, cardinality, ownership, snapshot boundaries, audit needs, and relationships to screening, submission, interviews, and commercial records. |
| V04-05 | Define candidate status and generic language expertise | V04-01 | Candidate-level status is separated from assignment state; language/framework/level model, migration implications for `jlptlanguage`, and V0.6 acceptance criteria are documented. |
| V04-06 | Define Recruitment Assignment state machine | V04-04 | Allowed states, transitions, terminal states, rejection paths, actor permissions, and transition audit events are approved; no implementation is included. |
| V04-07 | Define practical V1 RBAC model | V04-02 | Admin, manager, recruiter, and team-leader responsibilities are mapped to domain actions; authorization enforcement convention, tests, and migration/backward-compatibility implications are approved. |
| V04-08 | Define activity and audit-event architecture | V04-04 | ADR defines authoritative event ownership, event shape, retention/privacy constraints, and how business transitions are recorded without duplicate event logic. |
| V04-09 | Finalize deterministic database migration strategy | V04-01 | One migration execution path is selected; fresh-install, upgrade, failure, and rollback/recovery behaviour are specified; `schema.sql` responsibility is clear. |
| V04-10 | Define API and domain conventions | V04-03, V04-04 | Resource naming, versioning/prefix policy, error envelope, pagination/filtering, authorization and tenant-scoping conventions are documented. |
| V04-11 | Establish automated quality-gate acceptance criteria | V04-09 | Required backend/frontend/build/migration checks and the minimum GitHub Actions workflow scope are agreed; no CI is claimed until it exists and runs. |
| V04-12 | Conduct v0.4 architecture and UAT review | V04-02–V04-11 | Product owner and recruitment-domain reviewer confirm the v0.5/v0.6/v0.7 issue sequence, unresolved risks, and test/UAT approach; release decision is recorded. |

## Explicitly out of scope

Do not implement clients, requirements, assignments, screening, submissions, offers, joining, invoices, payments, replacement, a complete interview redesign, matching, external sourcing integrations, portals, WhatsApp, or advanced analytics in v0.4.

## GitHub labels

Apply `milestone:v0.4`, `architecture`, and `documentation` to every issue. Add one of `security`, `database`, `api`, `rbac`, `testing`, or `uat` where applicable.
