# SkillSifter v0.5.3 — CP11 + CP12 Go-Live Readiness

**Release:** v0.5.3  
**Scope:** CP11 Production Quality Gate + CP12 Recruitment Workflow UAT / Go-Live Readiness  
**Approach:** lean verification and stabilization; no new platform infrastructure

## 1. Release Intent

v0.5.3 closes CP11 and CP12 together. There is intentionally no v0.5.2 release.

This checkpoint does not introduce a new architectural layer. It verifies that the existing implementation is coherent, testable, tenant-safe, and ready for controlled go-live validation.

## 2. CP11 — Production Quality Gate

### Verification

- Backend formatting is enforced by CI.
- Backend repository structure and migration directory are validated by CI.
- Schema definitions and schema initialization are validated by CI.
- Backend build is validated by CI.
- Backend vet is validated by CI.
- Backend tests run with coverage.
- Backend coverage is published to the GitHub Actions job summary.
- Frontend dependency installation, lint, tests, and production build are validated by CI.
- Backend and frontend workflows remain separate and intentionally simple.
- Continuous deployment remains outside this checkpoint.

### Decision

**CP11: PASS — no additional CI machinery required.**

The existing quality gate already covers the useful release checks without adding unnecessary pipeline complexity.

## 3. CP12 — Recruitment Workflow UAT / Go-Live Readiness

The target recruiter workflow is:

```text
Candidate
  → Candidate expertise
  → Requirement
  → Recruitment Assignment
  → Screening
  → Submission
  → Interview
  → Decision
  → Commercial / Joining
```

### Validation matrix

| Area | Readiness target | Evidence / status |
|---|---|---|
| Candidate creation | Candidate can be created and maintained within tenant | Automated backend coverage present |
| Candidate status | Status is constrained to active/inactive/blacklisted/archived | Database constraint + regression coverage |
| Candidate expertise | Technical and language expertise use authoritative normalized tables | Migration + domain/handler coverage |
| Requirement | Requirement belongs to the tenant/client workflow | Existing domain/API implementation to be exercised in UAT |
| Assignment creation | Candidate can enter a controlled recruitment assignment | Assignment integration coverage present |
| Assignment ownership | Created/owned actors are tenant-authorized | Assignment authorization regression coverage |
| State transitions | Only supported assignment transitions are allowed | State-machine regression coverage |
| Screening | Assignment can progress through screening | Assignment workflow implementation to be exercised in UAT |
| Submission | Formal submission records required snapshot state | Snapshot + submission regression coverage |
| Interview | Assignment can progress into interview workflow | Existing implementation to be exercised in UAT |
| Decision | Outcome is represented by the assignment lifecycle | State transition coverage |
| Audit/activity | Important assignment lifecycle actions remain traceable | Audit regression coverage |
| Tenant isolation | Cross-tenant access/actors are rejected | Tenant-isolation regression coverage |
| Role authorization | Role boundaries are enforced for recruitment operations | RBAC/authorization coverage |
| Dashboard/reporting | Existing reporting reflects available transactional data where implemented | Validate during product UAT; no new reporting architecture added |

## 4. UAT Rule

CP12 is deliberately not a large automated browser-testing project.

The automated suite establishes the technical regression floor. Product-owner/recruiter UAT validates the actual user workflow in the running application. Any UAT failure is treated as a real product bug and fixed narrowly, with a regression test added when the failure belongs in automated coverage.

No speculative features, observability stack, distributed tracing, new infrastructure, or performance framework is introduced as part of CP12.

## 5. Security / Tenant Gate

Before production use, the following must be explicitly exercised with two tenants:

1. A tenant user can perform permitted recruitment operations inside their own tenant.
2. A user or actor from another tenant cannot be substituted into assignment operations.
3. Cross-tenant records cannot be read or modified through the recruitment workflow.
4. Role restrictions remain effective for recruiter, team leader, manager, and administrator boundaries.

## 6. Release Gate

v0.5.3 is considered technically release-ready when:

- CI is green.
- Database schema validation is green.
- Backend and frontend verification are green.
- No known blocking regression remains in the recruitment workflow.
- Manual recruiter UAT is completed against the running application before production cutover.

## 7. Operating Principle After v0.5.3

```text
LEAN → STABLE → LIVE → OBSERVE → FIX → OPTIMIZE → EXPAND
```

Only production evidence should justify additional performance, observability, infrastructure, or architectural work.
