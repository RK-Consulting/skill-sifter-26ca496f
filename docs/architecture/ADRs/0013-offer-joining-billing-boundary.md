# ADR 0013 — Offer, Joining, and Billing Boundary

**Status:** Accepted
**Scope:** Core SkillSifter recruitment workflow
**Runtime context:** Candidate × Requirement

## Context

Selection is the final decision point of the interview workflow, but selection alone does not create a commercial event.

SkillSifter must represent the downstream recruitment transaction from selection through offer, joining, and billing without introducing a global recruitment state onto Candidate and without reintroducing Recruitment Assignment as a runtime dependency.

The commercial rule is explicit:

> Selection alone is not billable. Billing is raised on the joining date.

SkillSifter remains a recruitment intelligence platform. Billing records may support recruitment-firm billing operations, but this phase does not turn SkillSifter into a general accounting, payroll, or employee HRMS system.

## Decision

Offer, Joining, and Billing are independent but sequential records anchored to the same Candidate × Requirement context.

```text
Selection
    |
    v
Offer
    |
    +--> declined / expired / withdrawn
    |
    v
Offer Accepted
    |
    v
Joining
    |
    +--> no-show / cancelled
    |
    v
JOINED
    |
    v
Billing
```

No Candidate master field represents offer, joining, or billing outcome.

### 1. Offer

An Offer can be created only when the Candidate × Requirement selection decision is `selected`.

Minimum authoritative context:
- tenant_id
- candidate_id
- requirement_id
- selection reference
- offer status
- offered date
- expected joining date
- offer details/notes
- audit timestamps

Recommended status vocabulary:
- `draft`
- `offered`
- `accepted`
- `declined`
- `expired`
- `withdrawn`

Rules:
- exactly one active Offer is permitted for a Candidate × Requirement;
- an Offer cannot be created for a rejected or missing Selection;
- only an accepted Offer can progress to Joining;
- declining, expiring, or withdrawing an Offer terminates that offer path without changing Candidate master state.

### 2. Joining

Joining represents the actual recruitment outcome for the Candidate × Requirement.

Minimum authoritative context:
- tenant_id
- candidate_id
- requirement_id
- offer reference
- joining status
- expected joining date
- actual joining date
- joining notes
- audit timestamps

The important distinction is between an expected joining date and an actual joining event.

Recommended status vocabulary:
- `scheduled`
- `joined`
- `no_show`
- `cancelled`

Rules:
- Joining requires an accepted Offer;
- only one successful Joining is permitted for a Candidate × Requirement;
- `joined` requires an actual joining date;
- the Candidate × Requirement transaction becomes `JOINED` when actual joining is recorded;
- no global Candidate status is changed to `joined`.

### 3. Billing

Billing represents the recruitment firm's commercial claim generated by the successful joining.

Billing is associated with:
- tenant
- candidate
- requirement
- client
- joining

Billing eligibility is created by the `joined` event, not by selection or offer acceptance.

**Billing date is the actual joining date.**

Minimum authoritative context:
- tenant_id
- candidate_id
- requirement_id
- client_id
- joining reference
- billing date
- billing amount/commercial basis
- currency
- billing status
- invoice/reference information
- due date where applicable
- audit timestamps

Recommended initial status vocabulary:
- `pending`
- `invoiced`
- `paid`
- `cancelled`

The billing model should remain deliberately smaller than an accounting ledger. GST, tax accounting, payment reconciliation, general ledger, and finance-policy engines are outside this core recruitment phase unless separately approved.

## Runtime gates

```text
Selection
  decision = selected
        |
        v
Offer may be created
        |
        v
Offer accepted
        |
        v
Joining may be created
        |
        v
actual joining recorded
        |
        +--> Candidate × Requirement = JOINED
        |
        v
Billing eligible
        |
        v
Billing date = actual joining date
```

The gates must be enforced by the database-backed domain services, not only by frontend state.

## Candidate master boundary

The Candidate remains a reusable master record.

```text
Candidate A
  ├── Client X / Requirement 101 → JOINED → BILLED
  └── Client X / Requirement 205 → Interviewing
```

The first transaction must not mark Candidate A globally as joined, billed, offered, or selected.

## Commercial boundary

The following are deliberately separate:
- Candidate compensation / offer package
- Recruitment firm's client billing terms
- Actual billing/invoice record

A candidate's offered compensation must not be treated as the recruitment firm's billing amount.

The Requirement budget must not automatically become the billing amount.

## API boundary

The authoritative V1 API should follow the existing Candidate × Requirement pattern:

```text
GET  /api/v1/candidates/{candidateId}/requirements/{requirementId}/offer
POST /api/v1/candidates/{candidateId}/requirements/{requirementId}/offer

GET  /api/v1/candidates/{candidateId}/requirements/{requirementId}/joining
POST /api/v1/candidates/{candidateId}/requirements/{requirementId}/joining
PUT  /api/v1/candidates/{candidateId}/requirements/{requirementId}/joining

GET  /api/v1/candidates/{candidateId}/requirements/{requirementId}/billing
POST /api/v1/candidates/{candidateId}/requirements/{requirementId}/billing
```

Exact mutation surface should be finalized with the domain state model before implementation.

## Database boundary

Offer, Joining, and Billing should be introduced through new migrations after migration 031.

Historical migrations must not be rewritten because migration checksums are part of the schema contract.

The new tables should use Candidate × Requirement foreign-key relationships and tenant-scoped uniqueness/indexes.

Historical Recruitment Assignment data remains available only for upgrade compatibility.

## Non-goals

This phase does not introduce:
- employee records
- payroll
- attendance
- leave
- employee benefits
- HRMS contracts
- internal approval hierarchies
- accounting ledgers
- general finance workflows
- GST/tax engines
- payment reconciliation engines
- client interview panels
- hiring-manager workflows

## Consequences

1. Offer, Joining, and Billing follow the same runtime architecture established by Screening, Submission, Interview, Feedback, and Selection.
2. A candidate can progress differently for different requirements.
3. Selection remains a recruitment decision rather than a billing trigger.
4. Actual joining is the single commercial gate for billing eligibility.
5. Billing remains recruitment-business functionality without turning SkillSifter into an accounting/HRMS product.
6. The next implementation work can proceed incrementally: Offer → Joining → Billing, with domain tests and database gates at each stage.
