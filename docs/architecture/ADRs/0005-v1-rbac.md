# ADR 0005: V1 Role-Based Authorization

**Status:** Accepted  
**Decider:** Product owner  
**Related issue:** #21

## Context

SkillSifter already has roles and JWT-based authentication, but authorization is only partially enforced. The current implementation carries a role in the JWT and provides a simple role middleware, while domain permissions are not yet expressed as a consistent V1 authorization model.

V1 needs practical permissions for the recruitment firm's operating roles without introducing an enterprise permissions engine.

## Decision

SkillSifter V1 will use a **small, explicit role-based authorization model** with four business roles:

- `admin`
- `manager`
- `recruiter`
- `team_leader`

Authorization is based on **domain actions**, not on a large configurable permissions matrix. Roles are the primary authorization boundary for V1, while tenant identity remains an independent security boundary as defined by ADR 0001.

No enterprise permissions engine, arbitrary per-user permission builder, or configurable policy language will be introduced in V1.

## Role Responsibilities

### Admin

Full tenant administration and operational access, including user/role administration, clients and requirements, candidates, recruitment assignments, interviews, offers, joining and closure workflows, business development, commercial records, reports, and tenant configuration.

Admin access remains tenant-scoped and must never bypass tenant isolation.

### Manager

Operational management across the tenant, including clients and requirements, candidate records, recruitment assignments, recruiter/team ownership and controlled reassignment, interview and offer progression, business development, and operational reports.

Manager cannot perform platform/tenant user administration unless explicitly granted by the V1 authorization contract.

### Team Leader

Supervisory recruitment access, including candidate records, recruitment assignments, screening and submission workflow, interview coordination and progression, team workload/operational views, and controlled team-level ownership actions.

Team Leader access is limited to the tenant and team scope established by implementation; it must not become an implicit tenant-wide administrative role.

### Recruiter

Day-to-day recruitment operations, including candidate creation and maintenance, candidate search and screening, candidate interest confirmation, recruitment assignments, submissions, interview scheduling/coordination, offer and joining follow-up, assigned client/requirement work, and relevant operational views.

Recruiter cannot administer users/roles or perform unrestricted tenant configuration.

## Domain Action Matrix

| Domain | Admin | Manager | Team Leader | Recruiter |
|---|---|---|---|---|
| Users / roles | Full | Read | None | None |
| Clients | Full | Create/update | Read/use | Read/use assigned |
| Requirements | Full | Full | Create/use within team scope | Create/use assigned |
| Candidates | Full | Full | Full within team scope | Create/update/use assigned |
| Recruitment assignments | Full | Full | Full within team scope | Create/update assigned |
| Screening / submissions | Full | Full | Full | Full assigned |
| Interviews | Full | Full | Full | Full assigned |
| Offers / joining | Full | Full | Full within team scope | Operational follow-up |
| Business development | Full | Full | Read/use as authorized | Limited/use assigned |
| Commercial / invoices / payments | Full | Full | Read | No administrative access |
| Reports | Full | Full | Team/operational | Operational/assigned |
| Tenant configuration | Full | Limited | None | None |

The exact endpoint-level mapping is an implementation concern, but every protected endpoint must map to one or more approved domain actions rather than relying on ad-hoc role checks.

## Enforcement Convention

Authorization must be enforced **after authentication and tenant identity establishment, before the protected domain operation executes**.

The implementation should centralize the reusable authorization convention rather than duplicating string comparisons throughout handlers.

```text
Request
  ↓
Authentication
  ↓
Authenticated user + tenant identity
  ↓
Role authorization / domain action check
  ↓
Tenant-scoped domain operation
  ↓
Response
```

A role check alone is never sufficient for tenant isolation. Tenant authorization and role authorization are separate invariants.

Client-supplied role, user, or tenant values must never override authenticated claims/context.

## Compatibility

Existing roles and JWT claims remain supported during the staged migration. Existing role names must be normalized to the V1 vocabulary where necessary rather than silently creating additional role variants.

Existing `RoleMiddleware` behavior may remain temporarily as a compatibility mechanism, but new implementation work should converge on the approved domain-action authorization convention.

The transition to tenant IDs defined by ADR 0001 must not weaken existing tenant filtering.

## Authorization Test Requirements

Automated tests must cover:

1. Each V1 role against each protected domain action.
2. Unauthorized role access returns a deterministic authorization failure.
3. Authenticated users cannot elevate their role through request payloads or URL parameters.
4. Tenant A users cannot access Tenant B resources regardless of role.
5. Admin privileges remain tenant-scoped.
6. Team Leader scope cannot silently become unrestricted tenant-wide access.
7. Recruiters cannot perform administrative actions.
8. Missing/invalid authentication is rejected before authorization.
9. Role and tenant claims cannot be substituted by client-supplied values.

Negative authorization tests are mandatory for protected operations.

## Implementation Boundary

This ADR defines the V1 authorization architecture only. It does **not** authorize broad handler rewrites, permission-engine adoption, database redesign, or UI permission redesign under Issue #21.

Implementation should be delivered through separately scoped issues using the approved role/action matrix.

## Consequences

### Positive

- Clear operational roles match the recruitment firm's real workflow.
- Authorization remains understandable and maintainable.
- Tenant isolation and role authorization remain separate security boundaries.
- The model is sufficient for V1 without enterprise-grade permission complexity.
- Authorization behavior becomes testable through a defined domain-action matrix.

### Trade-offs

- Some fine-grained organizational policies must wait for a later release.
- Team-level scoping requires an explicit implementation convention and must not be inferred from role alone.
- Existing ad-hoc role checks will need gradual consolidation.

## V1 Boundary

V1 intentionally does not include custom per-user permissions, configurable permission builders, enterprise policy engines, arbitrary role creation, or autonomous authorization decisions.
